# librefang-channels — Dispatch Benchmarks

**File:** `librefang-channels/benches/dispatch.rs`

Criterion benchmarks for the channel message dispatch hot paths in `librefang-channels`. These benchmarks measure the performance of three critical subsystems that run on every inbound and outbound message: JSON serialization, agent routing resolution, and cross-platform message formatting.

## Running

```bash
# All benchmark groups
cargo bench -p librefang-channels

# Single group
cargo bench -p librefang-channels -- serialization
cargo bench -p librefang-channels -- routing
cargo bench -p librefang-channels -- formatting
```

The binary target is auto-generated by Criterion via `criterion_main!`.

## Benchmark Groups

The suite is organized into three independent criterion groups. Each group can be run in isolation using the group name filter shown above.

### Serialization

| Benchmark | What it measures |
|---|---|
| `message_serialize` | `serde_json::to_string` on a `ChannelMessage` |
| `message_deserialize` | `serde_json::from_str::<ChannelMessage>` from a pre-serialized JSON string |
| `message_roundtrip` | Serialize then deserialize in a single iteration (end-to-end overhead) |

All three use the same sample message produced by the local helper `make_sample_message()`, which constructs a Telegram `ChannelMessage` with a `ChannelUser` sender, `ChannelContent::Text` body, and no metadata or thread association. This is a representative "average" inbound message — no optional fields are populated beyond the minimum, so these numbers represent a best-case baseline.

### Routing

| Benchmark | What it measures |
|---|---|
| `router_resolve_direct` | `AgentRouter::resolve` hitting a pre-registered direct route (`telegram` / `user-42` → specific agent) |
| `router_resolve_default_fallback` | `AgentRouter::resolve` with no matching route, falling back to the default agent |
| `router_resolve_binding_match` | `AgentRouter::resolve` evaluating a loaded `AgentBinding` with `channel` + `peer_id` match rules against a VIP user |
| `router_resolve_with_context` | `AgentRouter::resolve_with_context` performing multi-field matching including `guild_id` and `roles` via `BindingContext` |

The routing benchmarks set up the router from scratch in each benchmark function (before the timed loop), so measured time reflects only the resolution path — not agent registration or binding loading.

**Scenarios in order of expected cost:**

1. **Direct route** — fastest path; a HashMap lookup on `(channel, peer_id)`.
2. **Default fallback** — misses the direct map, falls through to the stored default `AgentId`.
3. **Binding match** — iterates loaded `AgentBinding` entries, evaluating `BindingMatchRule` fields (`channel`, `peer_id`).
4. **Context-aware** — the most expensive path; additionally checks `guild_id` and `roles` from a `BindingContext` struct using `Cow<str>` borrowed values.

### Formatting

| Benchmark | What it measures |
|---|---|
| `format_markdown_passthrough` | `format_for_channel(..., OutputFormat::Markdown)` — no-op identity path |
| `format_telegram_html` | Markdown → Telegram HTML conversion (bold, italic, code, links) on a multi-paragraph sample |
| `format_slack_mrkdwn` | Markdown → Slack mrkdwn conversion on the same sample |
| `format_plain_text` | Markdown → plain text stripping all markup |
| `format_telegram_html_short` | Telegram HTML on a short 12-character string — measures per-call overhead without parsing work |
| `split_message_short` | `split_message("Hello!", 4096)` — single-chunk fast path |
| `split_message_long` | `split_message` on 500 lines (~10 KB) with a 4096-char limit — exercises chunking and boundary detection |
| `default_phase_emoji_all` | Iterates all `AgentPhase` variants (`Queued`, `Thinking`, `tool_use("web_fetch")`, `Streaming`, `Done`, `Error`) through `default_phase_emoji` |

The multi-paragraph `SAMPLE_MARKDOWN` constant contains bold, italic, inline code, and links to exercise the formatter's parsing branches. The `SHORT_TEXT` constant (`"Hello world!"`) isolates fixed per-call overhead from per-byte parsing cost.

## Test Data

Two constants provide the formatting input corpus:

- **`SAMPLE_MARKDOWN`** — a 7-line markdown block with `**bold**`, `*italic*`, `` `code` ``, `[links](url)`, and bullet lists.
- **`SHORT_TEXT`** — `"Hello world!"`, used to measure baseline function call overhead.

The `make_sample_message()` helper constructs a `ChannelMessage` with `ChannelType::Telegram`, a single `ChannelUser`, `ChannelContent::Text`, and a current UTC timestamp. This function is called once before each serialization benchmark's timed loop.

## Dependencies on Library APIs

```
dispatch.rs
├── librefang_channels::formatter
│   └── format_for_channel(text, OutputFormat)
├── librefang_channels::router
│   ├── AgentRouter::new / set_default / set_direct_route
│   ├── AgentRouter::register_agent / load_bindings
│   ├── AgentRouter::resolve(channel_type, peer_id, thread_id)
│   ├── AgentRouter::resolve_with_context(..., &BindingContext)
│   └── BindingContext (constructed with Cow::Borrowed fields)
├── librefang_channels::types
│   ├── ChannelMessage, ChannelUser, ChannelContent, ChannelType
│   ├── split_message(text, max_len) → Vec<String>
│   ├── default_phase_emoji(&AgentPhase) → &str
│   └── AgentPhase (Queued, Thinking, Streaming, Done, Error, tool_use)
└── librefang_types
    ├── agent::AgentId (UUID, created via AgentId::new)
    └── config::{AgentBinding, BindingMatchRule, OutputFormat}
```

## Adding New Benchmarks

To benchmark a new hot path:

1. Add a `fn bench_<name>(c: &mut Criterion)` function following the existing pattern — call `c.bench_function(...)` with `black_box` on all inputs to prevent dead-code elimination.
2. Insert the function name into the appropriate `criterion_group!` macro (`serialization`, `routing`, or `formatting`).
3. If the new benchmark belongs to an entirely new category, create an additional `criterion_group!` and add it to the `criterion_main!` tuple.
